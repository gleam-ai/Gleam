# UI 验证方法论（强制）

三条，全部来自 2026-10-15 Gleam App 重构的真实教训。

## 一、注入验证优先于假设验证

改 UI 不只能"读代码觉得对"。代码里 `display:none`、token 未定义、钩子插错作用域，**全部静默失效**——不报错，只在渲染时消失。

做法：需要真实数据/真实状态时，用临时测试钩子注入（失败卡、待批准卡、低分卡、极端 accent），跑完**删除钩子并复验 served 产物里已无钩子**。判据：`curl /assets/app.js` 里搜不到钩子名。

本轮实例：`--state-run-rgb` 是否定义（读码以为有，运行时实测两个主题都有）；`window.__gleamTest` 插到 Hardware 模块 `return` 之后变成死代码（读码看不出来，运行时 `typeof` 为 undefined 才发现）。

## 二、无头验证不能信 show:false

Electron `new BrowserWindow({ show: false })` 的窗口，Chromium 按帧节流，`capturePage()` 会拿到**陈旧帧**——DOM 状态已变、画面还是旧的。表现为"harness 报告隐藏、截图显示可见"的幽灵矛盾。

正确做法：**离屏可见窗口**——`show: true` + `setPosition(-4000, 0)`，合成器正常产帧；必要时 `webContents.beginFrame()` 强制出一帧再拍。

排查纪律：截图与 DOM 探针矛盾时，**先信探针**（DOM 是权威），再用时间线探针（每 200ms 采样）证明行为稳定，最后才怀疑捕获层。本轮实例：横幅×筛选联动被误判了整整两轮，最后定位到捕获层。

## 三、「我扫描过了」类结论必须贴实际值

任何"全量核过""不存在""不会撞"的结论，必须附**实际值清单**（grep 结果、计算过程、运行时实测）。贴了数据的结论可以被证伪，没贴数据的结论只是语气。

本轮两个对照实例：

- **青色方案**：贴了 26 个 accent 的全量 hue 实测表 → 对方验算后承认自己引用了仓库里不存在的参考值，方案通过。
- **26° 色相警告**：只给了 HSL 色相角没算 ΔE → 对方算出 ΔE=31.9（可分辨），警告被撤回；但同一轮引出了真问题（L\* 仅差 1.1，CVD 下坍缩），用形态维度解决并实证。

**色相邻近 ≠ 分不开，ΔE 才是感知距离；两者都要算，算了都要贴。**

## 四、自检表格本身的数字也要可验算

自检报告的**分母**必须与清单实际条目数一致：新增清单项时同步更新分母，禁止照抄上一轮的分母。一个没人数过的分母，填再多次 ✅ 也只是仪式，不是质量保证。

本轮实例：GLEAM-DESIGN.md §13 写「反 slop 清单：18 项」，§12 逐条实数是 21 项（色彩 5 + 布局 5 + 字体 3 + 内容 5 + 动效 3）——连续多轮自检照抄「18/18」通过，直到有人真的去数。同轮第二例：二维码「模块仍 ≥2px」是 88/37 估的，最密那张（45 模块）88/45=1.96 已破线——**分母（模块数）取错，结论整条作废；数学只是估算，能实测就实测**（扫码用手机扫，不看换算）。
